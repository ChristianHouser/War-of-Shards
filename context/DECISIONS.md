# Design Decisions Log

Record every important decision here so future AIs (and you) never re-debate the same thing.

## Format
**Date** – Decision  
Reason / context

---

**2026-08-13** – Hero cards were resized (battlefield row height 58px → 72px; trimmed icon/type/HP font sizes; slimmer mana-bar padding).
Reason: The per-hero mana bar was already implemented and wired up correctly in JS, but the card's flex content was taller than the card's own box, so the mana bar silently overflowed past the bottom of the card and rendered behind the next row's card — it existed but wasn't visible. This was a layout bug, not a missing feature.

**2026-08-13** – Each hero's max mana equals the highest-cost ability they have access to, not a flat pool.
Reason: A flat 10-mana cap meant heroes could sit well above what they'd ever need to spend. Normal heroes (Basic Attack only) cap at `BASIC_COST` (3); special heroes (Basic + Special) cap at `SPECIAL_COST` (5). Revisit this if/when more ability tiers are added — the rule as implemented is "max = cost of your most expensive unlocked ability."

**2026-08-13** – "Do Nothing" extended to ALL player heroes, and every hero now acts once per turn (supersedes the earlier same-day decision that scoped it to special heroes only).
Reason: The turn flow was changed so the enemy turn starts automatically once every living player hero has acted (attacked or chosen Do Nothing) — see next entry. For that to work, every hero (not just specials) needs a way to explicitly declare "done," so the action popup (Basic / Special-if-unlocked / Do Nothing / Cancel) now opens for any hero the player taps, not just specials. A side effect: heroes can no longer attack more than once per turn — previously a hero could attack repeatedly as long as they had mana; now choosing an attack (or Do Nothing) locks them until the next player turn.

**2026-08-13** – Turn flow auto-advances: once every living player hero has acted, the enemy turn begins automatically.
Reason: Player is always the attacker, always on the left side; the enemy should never act until the player is done. Requiring a manual "End Turn" click after already using every hero was redundant friction. The End Turn button remains as a manual override for ending the turn before every hero has acted (e.g. deliberately banking mana on some heroes for next turn).

**2026-08-13** – Gem/hero color palette set to 5 colors: Red, Green, Blue, Yellow, Purple (previously 4: red, green, blue, gold).
Reason: Explicit request. "Gold" was replaced with Yellow, and Purple was added as the 5th. The per-side hero color distribution rule (at least 3 distinct colors among the 5 heroes, no more than 2 sharing a color) already existed in `isValidColorSet`/`generateSideColors` and satisfied the request as-is — only the `COLORS` array and matching CSS (tile colors, card gradients, color-dot swatch) needed updating.

**2026-08-13** – FINAL: "Do Nothing" is special-heroes-only. Normal heroes must attack if able, and are only exempt from blocking the turn when they truly can't act (not enough mana). This supersedes the earlier same-day decision that extended it to all heroes.
Reason: Direct instruction — "All characters on my side must use their attack if they can, except those with the option to Do Nothing. Only those with more than one attack option have that Do Nothing option." Normal heroes lost the action popup entirely and went back to direct-select (click hero → click enemy), matching the very first ask in this project. `checkAutoEndPlayerTurn()` now treats a normal hero as "resolved" if it attacked OR it has less than `BASIC_COST` mana (can't act at all); a normal hero that CAN act still blocks the auto-advance until it does.

**2026-08-13** – A player turn is now: (1) swap two tiles — exactly one swap, (2) attack with any character who can, (3) if no one can attack, the turn is over.
Reason: Direct instruction. Previously the player could swap tiles as many times as they wanted before ending their turn; now the board locks (dims via `#board-wrap.locked`) after one successful (match-creating) swap, and further clicks are blocked with a log message until the next player turn. A failed/reverted swap (no match) does not use up the turn's swap. `checkAutoEndPlayerTurn()` is now called immediately when the match cascade finishes, not just after an attack or Do Nothing, so the turn ends automatically the instant nobody is able to attack — matching "if no one can attack, turn over" without requiring a manual End Turn click. The existing per-hero resolution rules (special heroes need an explicit attack-or-Do-Nothing; normal heroes are exempt only when they truly can't afford to act) are unchanged and still govern what "no one can attack" means.

**2026-08-13** – Removed the "End Turn" button from the UI.
Reason: Direct instruction — with the turn structure now fully automatic (one swap → attack with anyone who can, or not → auto-advance the instant no one can act), there's no scenario left where the player needs to manually end their turn early. `endPlayerTurn()` the function is unchanged and still called internally by `checkAutoEndPlayerTurn()`.

**2026-08-13** – Melee/Ranged targeting restriction implemented in code for the first time.
Reason: CLAUDE.md and GAME_MECHANICS.md had documented "Melee units cannot attack enemy Ranged until the enemy Melee zone is cleared. Ranged units can attack any enemy." as a core rule since the project's design docs were written, but the actual combat code never enforced it — any hero could attack any enemy. The user's turn-order spec explicitly called this out as step 2.2, which surfaced the gap. Added `getValidTargets(attacker)`, applied to both the player's tap-to-attack flow (blocked target logs a message, no state change) and the enemy AI's target selection, so the rule now holds for both sides symmetrically.

**2026-08-13** – Fixed a turn-ending deadlock: a hero with less than `BASIC_COST` mana is now exempt from `checkAutoEndPlayerTurn()`'s "must resolve" requirement regardless of whether it's a normal or special hero (previously the exemption only applied to normal heroes).
Reason: The user reported the turn wasn't auto-ending even after attacking with everyone who could, leaving the ones who couldn't, and using Do Nothing on the special hero that had a real choice. Root cause: `onHeroClick`'s mana check (`if (h.mana < BASIC_COST) return;`) runs before the special-hero branch that opens the action popup — so a special hero with too little mana to even afford Basic Attack could never reach the "Do Nothing" button, meaning `actedThisTurn` could never be set for them, and the old logic (which only exempted normal heroes) waited on them forever. The fix makes the mana-based exemption apply to all heroes: "must attack or explicitly Do Nothing" only kicks in once a hero actually has enough mana for a real decision.

**2026-08-13** – The turn's swap is now enforced as mandatory, not just capped at one per turn.
Reason: Direct instruction — "I still need to do both: attack (if possible) and always swap two tiles." Mana carries over between turns (only `actedThisTurn` resets), so it was possible for a hero to have enough leftover mana to attack — or for every hero to already be "resolved" — before any swap happened this turn, letting the player attack (or the turn auto-end) without ever swapping. Closed both gaps: `onHeroClick` now refuses to select a player hero to attack until `swapUsedThisTurn` is true ("Swap two tiles first — attacks come after your swap."), and `checkAutoEndPlayerTurn()` now also requires `swapUsedThisTurn` before it will end the turn. This makes the sequence airtight: swap (required) → attack anyone who can → turn ends only once both the swap happened and no one can act.

**2026-08-13** – Removed randomization from character-card setup; hero colors, types, and special/normal assignment are now fixed per side.
Reason: Direct instruction — "Let's remove the randomization of the character cards." Replaced `generateSideColors()` (random, constraint-checked via `isValidColorSet`) and the random `pSpecials`/`eSpecials` index picks with fixed constants: `PLAYER_COLORS`/`ENEMY_COLORS` (one hero of each of the 5 colors per side) and `SPECIAL_INDICES = [0, 3]` (a fixed ranged + melee special per side). Deleted the now-unused `generateSideColors()`/`isValidColorSet()` functions. This only affects hero/character setup — the match-3 board tiles are untouched and still generate randomly, since that's core to the puzzle mechanic and wasn't in scope. `buildArmies()` now produces byte-identical heroes on every `resetGame()`.

**2026-08-14** – Split into two pages: `Roster.html` (character codex) and `Match_3_game.html` (the battlefield), sharing a new `characters.js` data module.
Reason: Direct instruction. `characters.js` holds the 35-character roster plus the shared combat constants (`BASIC_COST`, `BASIC_DMG`, `SPECIAL_COST`, `SPECIAL_DMG`) and `maxManaFor()`, loaded by both pages via `<script src="characters.js">`. The duplicate `const` declarations that used to live inline in `Match_3_game.html` were removed to avoid a duplicate-declaration collision now that both files load the same constants from one source. Roster.html is filterable (type/color) and searchable (name/ability text), and links to the battlefield; the battlefield links back to the roster.

**2026-08-14** – The old 5-hero, randomly-colored placeholder roster is retired in favor of 35 named characters across 16 classes.
Reason: Direct instruction — full roster (name, title, class, melee/ranged type, HP, color, damage type, weapon, and for ★ characters a named ability) transcribed into `characters.js`. Per the user's answer to a clarifying question ("roster now, simple abilities work, complex ones deferred"), all 35 characters are fully defined and browsable now, but only 4 abilities are mechanically wired into combat: Frenzy (Korr), Cheap Basic (Kael, Lumi), Divine Strike (Rorik), Brutal (Brick) — tagged via a `simpleAbility` field. The other 30 characters' Specials currently just deal the standard 5 mana → 2 damage; their ability text is shown on the Roster page with a "📜 Described" tag (vs "⚙ Implemented" for the working ones) so this isn't mistaken for a bug.

**2026-08-14** – Battlefield redesigned from 5 alternating melee/ranged slots per side to 6 dedicated Melee slots + 3 dedicated Ranged lanes per side (9 total per side, up from 5).
Reason: Direct instruction ("Melee columns should have 6 rows instead of 5"). Ranged units occupy one of 3 fixed lanes, each rendered as a card spanning 2 melee-row-heights. Melee occupies one of 6 slots; each slot is mapped to which ranged lane(s) it guards via `MELEE_SLOT_DEFS`: 2 slots aligned fully to lane 0 duplicated... (see next entry for the exact mapping and the half-step design). This also means the battlefield's per-side capacity is now 9, not 5 — noted as superseding the old flat "Max 6v6" framing for this specific screen (see TODO.md).

**2026-08-14** – Melee stagger/half-step coverage mapping finalized: slot 0 = aligned to lane 0, slot 1 = boundary covering lanes 0+1, slot 2 = aligned to lane 1, slot 3 = boundary covering lanes 1+2, slot 4 = aligned to lane 2, slot 5 = a second aligned guard for lane 2.
Reason: Answering the clarifying question "how should melee stagger in front of ranged," the user picked "half-step positions" — melee can align fully with one ranged lane (full cover of just that one) or sit on a boundary row between two lanes (partial/shared cover of both), with coverage being binary (no damage-reduction gradient). This exact 6-slot mapping was my own implementation choice to fit 6 physical slots against 3 lanes with at least one boundary row per internal seam (0/1 and 1/2) — it wasn't approved slot-by-slot by the user and produces a deliberate asymmetry (lane 0 gets 2 possible guards, lanes 1 and 2 get 3 each), since a perfectly symmetric split isn't achievable with exactly 6 slots, 3 lanes, and a working stagger system. Flagged in TODO.md for the user to weigh in on once they can see/play it.

**2026-08-14** – Melee/Ranged targeting protection changed from zone-wide ("melee can't reach ANY ranged until ALL enemy melee are dead") to per-lane ("melee can't reach a SPECIFIC ranged unit while a melee slot guarding that unit's lane is occupied").
Reason: Direct instruction — "While melee is partially or fully in front of a ranged character the ranged character cannot be attacked by opposing melee character." This is strictly more granular than the old all-or-nothing rule and is what makes the half-step stagger system meaningful: a single melee guard can now protect just its own lane(s) while other lanes remain open, rather than the entire enemy ranged line being locked down by any one surviving melee unit anywhere. Implemented via `getCoveredLanes(side)` (which ranged lanes currently have a living guarding melee) feeding into `getValidTargets()`. Ranged attackers are unaffected — always could and still can hit anyone.

**2026-08-14** – Added a deployment/placement screen: player builds their own team by tapping a character from their available roster, then tapping an empty slot of the matching type to place them (tap-to-place, not drag-and-drop).
Reason: Direct instruction, with drag-and-drop vs. tap-and-drop left to my judgment — chose tap-to-place since it's more reliable on touch devices, which matches the project's mobile-first priority (see TODO.md's "choose game engine" note). The player's selectable pool is the 35-character roster minus the 9 characters on the fixed enemy team (26 available); the enemy team is fixed (not random), consistent with the earlier "remove randomization" decision. Deployment is a separate step from resetting a battle in progress — "Restart Battle" keeps the current placement and just resets HP/mana/board, while a new "Change Deployment" button clears the battle and returns to the roster-picking screen.

**2026-08-14** – Win/lose detection unified inside `performAttack()` to check both outcomes after every attack, regardless of which side attacked.
Reason: Bug found while reworking combat for named characters — the old code only checked "did the player just win" inside the player's own attack path, and only checked "did the player just lose" once, at the very end of the enemy's whole turn (after all its attacks had already fired). Centralizing the check inside `performAttack()` means a defeat is now caught immediately after the exact enemy attack that causes it, not delayed until the turn's other attacks (which would be pointless/confusing to still process) finish.

**2026-08-14** – Ranged lanes increased from 3 to 5; Melee stays at 6 slots. Battlefield capacity per side is now 6 Melee + 5 Ranged = 11 (up from 9).
Reason: Direct instruction ("Ranged column needs 5 rows. Melee with 6 rows."). `MELEE_SLOT_DEFS` was rebuilt for the new 6-slot/5-lane ratio: slots 0, 1, 2, 4, 5 each align fully to one lane (0, 1, 2, 3, 4 respectively — every lane gets a dedicated guard), and slot 3 is the one remaining slot, placed as a boundary covering lanes 2 and 3. This is a smaller stagger budget than the previous 3-lane version (which had a boundary at every seam) — only the lane 2/3 seam currently has a half-step option, since there's exactly one "spare" slot once every lane has its aligned guard. `ENEMY_TEAM_IDS.ranged` was expanded from 3 to 5 ids (added Mireya and Caelum) so the fixed enemy team still fully occupies every ranged lane.

**2026-08-14** – Battlefield cards reverted from the very compact 44px/tiny-font design back to a "standard" uniform size (66px, larger fonts, mana bar with an overlaid number) for both Ranged and Melee.
Reason: Direct instruction ("Cards must have standard size"), with a forward-looking note that cards may eventually become 2D character art — so the current box-with-icon-and-text card is explicitly a placeholder, not a final look. This change coincided with dropping the CSS Grid row-spanning layout (which had forced Ranged cards to be double-height to visually align with 2 Melee rows) in favor of two independent flexbox columns — now that Ranged (5) and Melee (6) have different row counts, pixel-aligning them no longer made sense, and coverage was already fully data-driven (`MELEE_SLOT_DEFS`) rather than inferred from visual position.

**2026-08-14** – The player's deployment pool is now the full 35-character roster; picking a character does not depend on whether the enemy's fixed team also uses them.
Reason: Direct instruction ("Enemies can use characters but not restrict the user from selecting the same character") — supersedes the previous round's decision to exclude the enemy's 9 (now 11) fixed characters from the player's pool. A player can now field the same named character the enemy fields (a mirror matchup), if they choose to. The only remaining restriction is that a player can't place the same character into two of their own slots at once (already enforced — placing removes an id from `deployAvailable` until it's unplaced).

**2026-08-14** – Added Melee/Ranged filter chips + a Clear button to the deployment roster list.
Reason: Direct instruction. With the player's pool now the full 35 characters (up from 26) and always fully open, filtering became more useful for narrowing down what to browse. Two toggle chips ("⚔ Melee" / "🏹 Ranged") filter `deployAvailable` by type; clicking an already-active chip toggles it off. A separate "✕ Clear" button resets the filter to show everyone, requested explicitly rather than relying on re-toggling the active chip.

**2026-08-14** – Battlefield redesigned again: dropped all fixed slot/lane counts in favor of a single **team cap of 5 characters per side** (any mix of Ranged + Melee), with Ranged placed by tap-to-place (stacking top-to-bottom in placement order) and Melee placed by genuine drag-and-drop with a live coverage preview.
Reason: Direct instruction, based on 4 hand-drawn diagrams showing melee should be freely positionable either directly in front of one ranged character or straddling the gap between two adjacent ranged characters — "1. No more than 5 characters on each team. 2. ...the melee column is kind of flexible... Not sure how it should be handled visually or code wise." Asked a clarifying question on the visual/interaction model; the user's answer diverged from all three offered options: "I was thinking when they tap and drag the card, it should auto show what ranged characters it protects. While the user is dragging it in the Melee column." This requires real drag gestures, not tap-to-place, for Melee specifically. Ranged placement and stacking-guard questions were answered by accepting my recommended defaults (stack in placement order; multiple Melee may stack on the same lane/boundary). This entirely replaces the previous 6-slot/5-lane fixed-count model (and its `MELEE_SLOT_DEFS` static coverage table) from the two prior entries above — those are now historical, not current.

**2026-08-14** – Melee coverage is now a per-hero, dynamically-computed `coverage` object (`{type:'aligned', lane}` or `{type:'boundary', lanes:[a,b]}`) instead of a lookup into a fixed slot-definition table.
Reason: Once melee is drag-placed anywhere along the Melee column rather than into one of a fixed number of slots, there's no static slot index to key off of. `computeBandFromRects(rects, y)` is a pure function that takes the live `getBoundingClientRect()` results of the currently-placed Ranged cards plus the pointer's Y position and returns which lane(s) the drop point falls against (aligned to one card, or in the gap/boundary between two adjacent cards). This is invoked at drop time (and at reposition time, if an already-placed Melee card is dragged again) to set that hero's `coverage`. `getCoveredLanes()` was updated to read each living Melee hero's own `coverage` field instead of indexing into a slot table; `getValidTargets()` and all other targeting logic were unaffected since they only consume `getCoveredLanes()`'s output.
Verification note: drag-and-drop can't be exercised through real touch/mouse input in this environment. It was verified via (a) unit tests of `computeBandFromRects` against synthetic rects, and (b) full simulated pointer-event drag gestures in jsdom with `Element.prototype.getBoundingClientRect` monkey-patched to return realistic card positions. This exercises the whole preview → drop → coverage-assignment pipeline in code, but is not a substitute for testing the actual gesture on a touch device — flagged as the top item in TODO.md's Next Actions.

**2026-08-14** – `ENEMY_TEAM` rebuilt to exactly 5 characters (2 Ranged: Lumi, Saryn; 3 Melee: Korr, Rorik, Brick) to match the new `TEAM_CAP = 5`, replacing the previous 11-character (6 melee + 5 ranged) fixed enemy roster.
Reason: Direct consequence of the team-size cap dropping from 11 to 5 per side. The 5 enemy characters were deliberately chosen (not arbitrary) to keep all 4 mechanically-implemented simple abilities exercised in any playtest: Korr (frenzy), Lumi (cheapBasic2), Rorik (divineStrike), Brick (brutal). Their melee `coverage` was hand-assigned to demonstrate both coverage shapes: Korr aligned to lane 0, Rorik boundary covering lanes 0+1, Brick aligned to lane 1.

**2026-08-14** – Ranged placement changed from tap-to-place/stack-in-order to drag-to-any-of-5-fixed-slots; Melee coverage math reworked to resolve against that fixed grid (with gaps) instead of "however many Ranged happen to be placed."
Reason: Direct instruction — "1. I want user to either drag card to place of their choice. 2. Ranged column should show all five spots of choice. 3. Melee should allow user to freely drag up and down, with system showing what ranged is protected (up to two ranged at the same time) while the user drags it up or down. 4. Melee can protect up to two ranged, as long as both ranged are together and melee is partially in front of both." Point 4 is effectively confirming the existing boundary-coverage behavior from the previous round, but points 1–2 change Ranged from a stacking list to a fixed 5-slot grid the player drags into and picks a spot on — this can leave gaps (e.g. a Ranged hero in slot 3 with slots 0–2 empty). `playerPlacements.ranged` changed from a growable array (index = placement order) to a fixed-length `RANGED_SLOTS`-sized array (`charId | null`, index = slot/lane number).
Consequence for Melee coverage: since Ranged slots can now be sparse, the boundary-coverage rule needed to explicitly account for empty slots. Split the old single `computeBandFromRects` into `computeSlotBand` (pure geometry — which of the 5 fixed slots, or which boundary between two adjacent ones, a Y position falls in, independent of what's filled) and `resolveMeleeCoverage(band, filledMask)` (turns that geometric band into actual coverage): a boundary between two filled neighbors covers both; a boundary where only one neighbor is filled covers just that one; a boundary between two empty slots covers nothing. This is a direct implementation of "as long as both ranged are together" — "together" means both physically adjacent slots are occupied, not just adjacent in geometry.
Ranged and Melee are now symmetric in interaction model (both drag-and-drop) but asymmetric in placement freedom: Ranged snaps to one of 5 discrete, always-visible slots; Melee remains a continuous free-form column with no slots of its own, per the user's explicit "freely drag up and down" wording for Melee specifically.

**2026-08-14** – Melee column on the deployment screen now renders sorted by `primaryLane(coverage)` instead of raw insertion order.
Reason: Bug report — "Melee column should allow the user to place a card anywhere in that column, not just at the top." The deployment screen's Melee rendering never adopted the lane-based sort that `renderBattlefield()` (the live-battle view) already used; it rendered `playerPlacements.melee` in push/array order instead, so a card's visual row was fixed by when it was placed, not by where it was dropped — repositioning only changed the stored `coverage`, never the array position, so a card could be dragged anywhere and it would still render in its original slot in the list. Fixed by sorting a `{entry, originalIndex}` view of the array by `primaryLane` at render time (keeping the real array index for the drag/reposition/remove handlers), matching the live-battle view's existing behavior. Ranged is unaffected — it already renders by fixed slot index, which is inherently drop-position-accurate.

**2026-08-14** – Corrected the Melee free-positioning fix: card position in the column is now driven directly by drop Y coordinate (array insertion index), completely decoupled from `coverage`, instead of being derived from it via a sort.
Reason: The prior same-day fix (sort the Melee column by `primaryLane(coverage)`) was reported as not working. Diagnosis: that sort makes visual order a *function of* coverage, but coverage and position are conceptually different things — when no Ranged units are placed yet (the exact state in the user's screenshot), every Melee card's coverage is `null`, so the sort has nothing to differentiate on and falls back to insertion order, reproducing the original "always near the top" symptom. Replaced with `computeMeleeInsertIndex(y, excludeIndex)`, which counts how many other currently-rendered Melee cards sit above the drop point and uses that count as the literal array insertion index — `playerPlacements.melee`'s array order is now rendered directly with no sort, so it IS the on-screen order. Coverage is computed independently, exactly as before. This makes the two concerns fully orthogonal: a card's row is about where you dropped it; its coverage tag is about what it's protecting — a card can occupy any row with any coverage (including none).
Also, per the same message: enemy Melee/Ranged columns are now vertically centered (`justify-content:center`, via a new `.center-content` class) instead of top-aligned, so a short fixed enemy roster doesn't look pinned to the top of a taller column. Applied to both the deployment screen and the live battle view; the player's own columns are unaffected.

**2026-08-14** – Found and fixed the actual root cause of "only one place to put Melee": `#battlefield` was using `align-items: flex-start`, so the Melee drop zone's real bounding box (the same `.bf-column` element the drop-detection code tests the pointer against) was only ever as tall as its own current content — a tiny box with 0-1 Melee placed. Changed to `align-items: stretch` so all 4 columns match the tallest one (the Ranged column's fixed 5-slot height).
Reason: Two prior fixes this same day (sort-by-coverage, then position-by-drop-index) both addressed the placement *math*, which was never actually broken — verified correct by jsdom tests both times. The real bug was a CSS layout issue: dropping below the Melee column's tiny actual box registered as "outside the drop zone" and got treated as a cancel/removal, regardless of how correct the underlying insertion-index math was. This class of bug is invisible to the jsdom tests used throughout this session, since every one of them monkey-patches `getBoundingClientRect` to fake positions rather than running a real layout engine — so the tests were faithfully verifying logic against layouts that don't match the real page. Verified this round with Playwright + real headless Chromium instead: confirmed the Melee dropzone's actual computed rect now matches the Ranged column's (365px, same top/bottom) with zero Melee placed, and performed real `mouse.down/move/up` drags to the top and bottom of that zone, both landing correctly. Added a `.bf-column.dropzone-hint .card.empty-slot` CSS rule so the "drag here" placeholder itself also visually fills the stretched height, instead of sitting above an unexplained empty gap.
Side effect (a fix, not a regression): this is also what makes the earlier "move enemy layout to the middle" change actually visible — `justify-content:center` (added to the enemy columns earlier the same day) had no visible effect while a column's box was exactly as tall as its content; now that all columns stretch to the Ranged column's height, the enemy cards visibly center within the extra space.

**2026-08-14** – Melee placement rebuilt a third time: position (`band`) and mechanical protection (`coverage`) are now fully separate per-hero fields, and placed Melee cards are absolutely-positioned to be pixel-level with the Ranged row (or half-step gap) they're on.
Reason: Direct clarification after the CSS drop-zone-size fix still didn't satisfy the request: "I should be able to place the card in the same 'row' as the ranged character, OR put it a half step down or up to be half in front of two ranged characters." This reveals the actual intended design was never "a free-floating ordered list" (the previous fix) — it's a literal visual snap to the Ranged grid, exactly two placement modes (full row, or half-step between two adjacent rows), matching the original hand-drawn diagrams from the start of this feature. `band` (geometry: which Ranged slot index, or which adjacent pair) is now stored per Melee hero and is always resolvable since the Ranged slot grid is a fixed, always-rendered `RANGED_SLOTS`-length structure regardless of what's filled. `coverage` (what's actually protected) is derived on demand from `band` + current fill state, rather than frozen at drop time — so placing a Melee hero next to a not-yet-filled Ranged slot now correctly starts protecting automatically once that slot fills, without needing to re-drag.
Rendering changed from normal-flow list order to `position:absolute` cards inside the (already-stretched) Melee column, with each card's `top` computed directly from the real on-screen rect of the Ranged slot(s) its band refers to — this is what makes "same row" a literal, verifiable visual fact rather than an approximation. Cards sharing a band fan out with a small offset (stacking is still allowed). Drag feedback now shows two tiers: gold for "you'll snap here" (the raw band, filled or not) and green for "and this is actually protected" (only for filled slots).
This obsoletes the array-order-based positioning system from the same day's earlier fix (`computeMeleeInsertIndex`) entirely — array order in `playerPlacements.melee` no longer has any visual meaning.

**2026-08-14** – Widened the boundary (half-step) hit zone in `computeSlotBand` from the ~4px CSS gap between Ranged cards to a generous, pitch-relative band centered on the midpoint between two adjacent slots' centers.
Reason: Direct feedback after testing the row/half-step snapping feature — "it's not easy to put it in front of two ranged characters." The boundary target had been the literal visual gap between two Ranged cards (`rects[i].bottom` to `rects[i+1].top]`), which is only the CSS `gap: 4px` — a few-pixel-tall touch target, unrealistic to hit reliably. Rewrote around slot centers: `BOUNDARY_FRACTION = 0.6` means 60% of the pitch between two adjacent centers now counts as boundary territory (roughly ±21px for the current 66px-card/4px-gap layout), with the remaining 40% split evenly as "aligned" zones nearest each center. This is a pure hit-testing change — band/coverage shapes, drag highlighting, and row-snapped rendering are unaffected, only which pointer Y positions map to which result. Verified in a real browser: a drop 15px off the exact midpoint (well outside the old target) now correctly resolves to boundary coverage of both neighbors, while a drop near a card's own center still resolves to aligned coverage of just that one.

**2026-08-14** – Added a third deployment filter chip, "★ Heroes", filtering by `isSpecial` rather than by Melee/Ranged type.
Reason: Direct instruction — "Create a third filter: Heroes. all of the characters with special abilities are heroes." `isSpecial` was already the field driving the ★ marker and named-ability display throughout the project, so this reuses it directly rather than introducing a new concept. Mutually exclusive with the existing Melee/Ranged chips (same toggle/Clear behavior), since a Hero can be of either type. Noted in TODO.md that 32 of the 35 characters are currently `isSpecial`, so this filter only excludes 3 — not a bug, just the current roster's composition.
